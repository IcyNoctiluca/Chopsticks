# Chopsticks classic-v1 - Analysis Report

Reproducible analysis of the `classic-v1` ruleset. Generated by `analysis/enumerate.ts` (exhaustive state-space enumeration + retrograde analysis).

## Method

1. **Enumeration.** Breadth-first search from the opening `A:[1,1] B:[1,1] turn:A`, applying every legal move via the engine's `getLegalMoves` / `applyMove` to discover all reachable states.
2. **Game graph.** Each state maps to its successor states (one per legal move).
3. **Retrograde analysis.** Backward induction from terminal states over the game graph, with cycle handling:
   - Terminal state (a `winner` is set) → **LOSS** for the player to move (the previous mover won).
   - A state is **WIN** if any successor is LOSS for the opponent.
   - A state is **LOSS** if all successors are WIN for the opponent (and it has at least one move).
   - A state is **DRAW** if it is neither WIN nor LOSS — i.e. the player to move can avoid losing (e.g. by cycling) but cannot force a win.
4. Values are recorded from the perspective of **the player to move**.

The implementation lives in `analysis/enumerate.ts` and is deterministic and reproducible.

## Opening balance

The starting position `A:[1,1] B:[1,1] turn:A` is a **DRAW** under perfect play. There is **no first-player advantage**: all six legal opening moves lead to a DRAW for the player who made the move.

| Opening move (A's move) | Result for A |
| --- | --- |
| tap L -> self R | DRAW |
| tap L -> B L | DRAW |
| tap L -> B R | DRAW |
| tap R -> self L | DRAW |
| tap R -> B L | DRAW |
| tap R -> B R | DRAW |

The opening is therefore **acceptably balanced**.

- `A:[1,1] B:[0,0] turn:B winner:A` (dist 5)
- `A:[2,1] B:[0,0] turn:B winner:A` (dist 5)

## Cycles and draw behaviour

Because `classic-v1` permits repetition (Phase 00 decision 8: "Allowed; no special loop rule"), 496 states are reachable from the opening in which the player to move can avoid losing by cycling but cannot force a win. Under perfect play the game can therefore continue **indefinitely** without a winner.

**Defined behaviour for `classic-v1`:** there is **no automatic draw**. A game ends only when one player has both hands dead. If both players choose to cycle, play continues without a declared result; the game has no draw outcome within this ruleset.

**Accepted risk / follow-up.** This is acceptable for the local two-player MVP (players simply stop). It is **not** acceptable for authoritative online play (Phase 07), where a game can lock into an infinite loop. A draw mechanism — for example three-fold repetition or a move cap — will be added as a **separate future ruleset variant** (e.g. `classic-tournament-v1`) or as a server-side match policy in Phase 07. `classic-v1` itself is frozen untouched.

This satisfies the Phase 04 criterion "known cycles and draw handling have defined behaviour": the behaviour is defined as "no automatic draw; play continues; no draw outcome," and the online-play gap is logged as a scheduled follow-up with a clear owner.

## Repetition / cycles

Repetitive positions are reachable (496 DRAW states). The ruleset intentionally provides no draw-by-repetition, in line with the Phase 00 decision and the engine's lack of a `draw` terminal status. The state space is finite (1142 states), so infinitely long games are possible only by revisiting states.

## Comparison with playtest (Phase 03)

- Playtest via scripted simulation ended in 8 moves with a winner (B). This is consistent with the analysis: the **shortest** path to a terminal is at most 8 moves, and imperfect play reaches a terminal quickly.
- No rules discrepancy was observed between the CLI playtest and the solver.
